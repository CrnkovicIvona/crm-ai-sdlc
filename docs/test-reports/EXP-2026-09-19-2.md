## Exploratory findings

Confidence and severity are separate.

### Login aside as the product

**Observed:** `/` redirects to `/login`. Visible product is
“BankCRM login” plus ADMIN/VIEWER aside (emails, roles, note that
only these two test users exist “as required by the specification”).
Empty Log in: native `Please fill out this field.` (email). Fake
identity: `Authentication failed.`

**User might think:** the bank only has two employees; pasting the
aside is the official UX; “full access” means something broader
than CRM clients.

**Classification:** QUESTION (spec silence) + OBSERVATION (intended
practice login). Confidence high. Severity high if treated as a
real bank; low as a practice app. Not a security BUG per skill.

### First screen is a dense PII table with machine timestamps

**Observed:** After VIEWER login, URL `/app/clients`, pager `1 / 31`,
no New. Created column values like
`2026-09-16T09:23:20.228265+00:00` (same raw form on VIEWER
detail Created). Search has visible label “Search” but no
placeholder/aria-label.

**User might think:** dates failed to format; this is an admin
debug screen, not a CRM.

**Oracle:** CRM-001 requires `created_at` as a field; it does not
require a human date format.

**Classification:** IMP. Confidence high. Severity medium for
first-time clarity. More investigation: no.

### VIEWER `/new` is silent

**Action:** open `/app/clients/new` as VIEWER.

**Observed:** URL becomes `/app/clients`; list; no alert/toast.

**User might think:** create is broken.

**Oracle:** VIEWER must not create; redirect is consistent with
existing CRM tests. Functionally OK.

**Classification:** IMP (clarity). Confidence high. Severity
low–medium.

### VIEWER detail vs ADMIN edit (mental model of permission)

**ADMIN:** `Edit client`, inputs, Save, Delete, optional products.

**User might think:** VIEWER is a different app; or that “Read-only
access.” is trustworthy (UI). **Must not claim** API enforcement

**Classification:** OBSERVATION (UI permission). Confidence high.
Authz remains PARTIALLY EXPLORED.

### Dashboard: period-insensitive Active next to period New

**VIEWER Last 30 (default):** Active 620, New 620, Churned 0, Rate
`N/A`, Net +620. Active hint: “Current number of clients that are
not soft-deleted.” Churn Rate card: **no** hint that `N/A` means
opening base 0. DASH-001 says cards should have a tooltip or short
explanation where `N/A` is ambiguous.

**Last 7:** Active still 620, New 521, Churned 0, Rate **`0%`**, Net
+521. Charts shrink to 2026-09. Adoption stays 19.8%.

**User might think:** Last 30 maths is wrong (Active cannot equal
New); or Last 7 “fixed” churn rate; or Active is a period metric
because it sits in the same KPI row.

**Oracle:** Active is current stock; `N/A` when opening base is 0 is
specified; Last 7 opening base > 0 with 0 churned ⇒ 0% is
consistent. Filters **do** change New (620→521) — “filters are
dead” **disproven**.

**Classification:** IMP / QUESTION (explain `N/A` and that Active
is not period flow). Confidence high on numbers. Severity medium
for a KPI screen. Related: BUG-004 makes the VIEWER Last 30
paradox worse (churn hidden).

### Custom range start after end

**Action:** Custom start `2026-09-19`, end `2026-09-01`.

**Observed:** No validation message. New 0, Churned 0, Rate **`0%`**
(not `N/A`), Net 0, Active still 620, both charts “No months in the
selected range.” Product table still populated. Then start
`2026-09-18` end `2026-09-19`: New 48, Rate 0%, Net +48.

**User might think:** custom dates do nothing useful, or the
dashboard is broken, or Rate `0%` vs Last 30 `N/A` is random.

**Oracle:** Custom is `[start date, day after end date)` in UTC;
inverted interval is empty for events; opening base can still be

> 0 at the later start ⇒ 0% churn. Spec does not define an invalid
> range error.

**Classification:** IMP / QUESTION. Confidence high. Severity
medium for first-time custom use.

  counts; inverted custom; dirty discard.
