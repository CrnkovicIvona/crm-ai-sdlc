# REQ-001: Bank employee access to BankCRM

- Work item: AUTH-001
- Issue: [#5](https://github.com/CrnkovicIvona/crm-ai-sdlc/issues/5)
- Status: Specified (human BD/TD recorded; Definition of Ready not given)
- Author: Agent from the business request; decisions BD-001–BD-008
  and TD-001–TD-008 approved by a human (BD-008 / TD-008 recorded
  2026-08-22). Definition of Ready is **not** recorded.

## Problem

Bank employees need to log into BankCRM before they can use the
application. Access must be limited to authenticated users. Employees
have two roles with different access. Employees must be able to log
out.

## Stated requirements

Quoted from the original human business request:

1. Bank employees need to log into BankCRM before they can access the
   application.
2. The application has two user roles: ADMIN and VIEWER.
3. An ADMIN user has full access to the CRM.
4. A VIEWER user has read-only access.
5. Only authenticated users may access the CRM.
6. Users must be able to log out.

## Approved clarifications (BD-001–BD-008)

These do not replace the stated requirements; they resolve prior
open questions.

- **BD-001:** Employees authenticate with **email and password**. SSO
  and MFA are out of scope for AUTH-001.
- **BD-002:** No in-app employee provisioning. Provisioning is
  external/system administration.
- **BD-003:** Exactly one role per employee: ADMIN or VIEWER; not both.
- **BD-004:** Failed authentication uses a **generic** failure
  message and must **not** reveal whether a particular account
  exists. Lockout is out of scope.
- **BD-005:** Explicit logout ends authenticated access. Automatic
  session timeout is **deferred** (future security/session decision).
- **BD-006:** ADMIN may perform permitted CRM **read** and **write**
  operations. VIEWER may perform permitted CRM **read** operations
  and may **not** write. AUTH-001 introduces **no** CRM business
  resources or CRUD modules. Future CRM resources must follow this
  model.
- **BD-007:** Unauthenticated users may access **only the login
  surface**. CRM requires authentication. After logout, the user must
  authenticate again before CRM access.
- **BD-008:** If an Auth session exists but the corresponding
  `profiles` record or a usable ADMIN/VIEWER role does not, the
  application **fails closed** and **denies protected CRM access**.
  No provisioning UI. Exact copy is not specified.

Meaning of original “full” / “read-only” is BD-006. It still does not
invent CRM modules.

## Out of scope

- SSO, MFA, password reset
- In-app user/role provisioning (BD-002)
- Account lockout (BD-004)
- Automatic session timeout (BD-005, deferred)
- Remember-me, multiple devices, concurrent sessions
- Any CRM business module beyond access control (BD-006)
- Exact error-message wording (generic failure is required; the
  string is not)
- Branding or languages

Technical stack is not a business requirement. It is in the technical
specification, decision log, and ADRs.

## Open questions

Resolved by BD-001–BD-008: former questions 1–5, 7 (as a permission
model without modules), and 8; logout-again is BD-007 / FR-008.

**Deferred, not blocking AUTH-001 implementation of this increment:**

- Automatic session expiration policy (BD-005)
- Exact authentication-failure copy (BD-004 requires generic only)
- Browser back-button / cache after logout (logout-then-reauth is
  required; cache behavior is not specified)
- How external administrators create users and `profiles` rows
  (BD-002; operational, not an AUTH-001 feature)
- Observable ADMIN write vs VIEWER read on **concrete screens** until
  a future CRM resource exists (BD-006)

## Implementation scope (this increment)

- Email + password login
- Generic failed-login feedback without account enumeration
- Denial of CRM when not authenticated; login surface only when
  unauthenticated
- Fail-closed denial when a session exists without a usable profile
  or role (BD-008)
- ADMIN vs VIEWER permission model (no CRM modules)
- Logout, then CRM denied until login again

Out of scope until a human adds it: provisioning UI, password
policies, SSO, MFA, lockout, timeout, CRM data features.

How AUTH-001 is implemented: technical specification. File-level
rollout: implementation plan after Ready.
